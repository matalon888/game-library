# V2 Design Record — Forecast, Configure, Operate

## Human feedback

The initial prototype was visually successful but strategically shallow. Repeated action responses and unconstrained random-event selection made the experience feel like clicking buttons instead of operating a system.

The approved V2 direction combines two educational layers:

- Founder attention: product, marketing, safety, support, funding, optimization, and rest
- AI operations: market forecasting, pricing, model selection, RAM, GPU throughput, caching, monitoring, burst compute, revenue, costs, utilization, latency, and churn

## Original design boundaries

The game uses the general educational pattern of gathering information, purchasing capacity, setting a price, operating, and reviewing results. It does not copy another game’s text, assets, characters, layouts, code, exact formulas, or audiovisual expression.

## Player verbs

- Read a forecast
- Configure the product
- Buy infrastructure
- Allocate founder attention
- Run the shift
- Reconcile the report
- Adapt the next day

## Anti-repetition policy

- Fourteen news items are shuffled and dealt without replacement.
- The deck reshuffles only when exhausted.
- An incident cannot occur twice in succession.
- Incidents require relevant simulation conditions.
- Operations reports are generated from the player’s actual configuration and demand rather than fixed response copy.

## Build Week explanation

The learning happens through visible cause and effect: marketing can create an outage, expensive models can erase margins, RAM and GPUs can create different bottlenecks, excess infrastructure can waste runway, and safety or support investments can improve retention and trust.
